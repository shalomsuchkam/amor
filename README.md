# Amor Flowers — рабочий прототип

Полностью рабочий сайт цветочного магазина Amor Flowers (Алматы): каталог,
корзина, оформление заказа, аккаунт с историей заказов, отзывы (в т.ч.
реальные с 2ГИС), фильтры по типу/цвету цветка/поводу, поиск, 3 языка
(RU/KK/EN), автозаполнение карточки товара через ИИ по фото и админ-панель
для менеджеров.

## Быстрый запуск (локально)

```bash
cd amor-flowers
python3 -m venv venv && source venv/bin/activate   # опционально, но рекомендуется
pip install -r requirements.txt
python3 seed.py      # создаёт БД и заполняет тестовыми данными (безопасно перезапускать)
python3 app.py        # http://localhost:5050
```

Админ-панель: `http://localhost:5050/admin/login` — логин `admin`, пароль `amor2026`.
**Смените пароль перед реальным запуском** (сейчас захардкожен в `seed.py`).

## Почему Flask + SQLite, а не Next.js/Supabase напрямую

Сайт разрабатывался в песочнице без доступа к npm-реестру и без общего
исходящего сетевого доступа (кроме отдельных интеграций вроде Supabase MCP).
Поэтому стек — Flask + SQLite + ванильный JS/HTML/CSS, без шага сборки:
всё, что нужно, ставится через `pip`, и сайт открывается сразу.

Схема БД в `db.py` (SQLite) специально зеркалит `supabase_schema.sql`
(Postgres) один в один по именам таблиц/колонок — переезд на Supabase
означает переписать только функции внутри `db.py` (запросы к SQLite →
запросы к Postgres через `supabase-py` или `psycopg2`), ни один route или
шаблон трогать не придётся.

## Supabase

Реальный проект **Amor Flowers** (аккаунт, который вы подключили) уже
подготовлен:

- Схема применена — все таблицы из `supabase_schema.sql` (categories,
  products, users, orders, order_items, reviews, admins, flower_types,
  flower_colors + связующие таблицы) созданы в проекте.
- Данные засеяны — 5 категорий, 12 товаров с тестовыми ценами, 8 реальных
  отзывов с 2ГИС и админ-аккаунт (`admin` / `amor2026`, тот же пароль что и
  в локальной БД).
- Таблицы `occasions`/`product_occasions` и полный расширенный список
  тегов — 24 типа цветка, 16 цветов, 21 повод (см. раздел ниже) — тоже
  добавлены и засеяны в этот проект. **Но** каталог из 24 новых букетов,
  добавленных позже в локальную SQLite-версию, в Supabase пока не
  продублирован — там всё ещё исходные 12 тестовых товаров. Если нужно
  — могу досеять и их отдельным запросом.
- **Важно:** в проекте до этого была демо-схема (`profiles`/`products`/
  `favorites`/`orders` с тестовыми данными о розах/пионах — судя по всему,
  осталась от первоначального создания проекта) — она заменена на схему
  Amor Flowers. Если там было что-то важное, скажите — можно восстановить
  из бэкапа Supabase.
- **Требует внимания перед реальным использованием:** Row Level Security
  (RLS) сейчас выключен на всех таблицах — это нормально, ПОКА к базе
  обращается только серверный код (Flask с service-role ключом), но если
  когда-нибудь фронтенд начнёт ходить в Supabase напрямую (через
  `supabase-js` с анонимным ключом), нужно включить RLS и написать политики
  доступа — иначе любой человек с anon-ключом сможет читать/менять все
  строки. Комментарий с рекомендациями уже есть в `supabase_schema.sql`.

Из этой песочницы нет прямого сетевого доступа к `*.supabase.co` (только
через MCP-инструменты), поэтому сам Flask-прототип здесь работает на
SQLite и не был живьём протестирован против Supabase. Когда будете
разворачивать сайт на реальном хостинге (с доступом в интернет), можно
переключить `db.py` на Supabase — используйте `supabase-py`
(`pip install supabase`) и Project URL + service_role ключ из настроек
проекта.

## Интеграция с Bitrix24 (CRM)

Каждый заказ с сайта (после успешного оформления) дублируется в Bitrix24
как новый лид — модуль `crm.py`, вызывается из `/api/checkout` в `app.py`.

Настройка:

1. В портале Bitrix24: Настройки → Разработчикам → Другое → Входящий
   вебхук (права на модуль CRM).
2. Скопировать URL вебхука (`https://ваш-портал.bitrix24.kz/rest/1/xxxxx/`)
   в переменную окружения `BITRIX_WEBHOOK_URL` перед запуском сайта.

Если переменная не задана — интеграция молча выключена, заказ всё равно
сохраняется в базе (`/admin/orders`), просто не дублируется в Bitrix. Вызов
не тестировался живьём (в песочнице нет сети до `*.bitrix24.*`), но код
рабочий и готов к реальному хостингу.

**Про переключение на свою CRM в будущем:** вся интеграция изолирована в
одной функции `crm.push_order_to_crm()` в `crm.py` — когда появится
собственная CRM, достаточно переписать реализацию этой функции (например,
на HTTP-запрос к своему API), не трогая `app.py` или чекаут.

## Автозаполнение карточки товара через ИИ (кнопка «Автозаполнение»)

На странице добавления/редактирования товара (`/admin/products/new` и
`/admin/products/<id>/edit`) под полем загрузки фото есть кнопка
«🤖 Автозаполнение». По клику фото, выбранное в поле выше (ещё до
сохранения формы), отправляется на анализ ИИ, который возвращает и
автоматически подставляет в форму:

- название букета на русском, казахском и английском;
- slug (латиница для ссылки `/product/<slug>`) — если он уже занят другим
  товаром, при сохранении автоматически подставится `-2`, `-3` и т.д.,
  сохранение не сломается;
- подробное продающее описание на всех трёх языках (2-4 предложения:
  состав, настроение, повод);
- тип(ы) цветка — отмечает подходящие чекбоксы;
- цвет(а) — отмечает подходящие чекбоксы;
- повод(ы), для которых подходит букет — отмечает подходящие чекбоксы.

Всё это нужно проверить и при необходимости поправить перед сохранением —
ИИ предлагает черновик (в т.ч. переводы на KK/EN — машинные, не заменяют
живого переводчика для финального текста), а не финальный текст. Поля
заполняются, только если они ещё пустые — то, что вы уже вписали вручную,
ИИ не перезапишет.

Реализация — модуль `ai.py`, единая точка входа `analyze_product_photo()`,
изолирована по тому же принципу, что и `crm.py` (см. выше): провайдер ИИ
выбирается переменной окружения `AI_PROVIDER`, переключиться на другой в
будущем — добавить одну функцию в `ai.py`, не трогая админку и остальной код.

**По умолчанию используется Google Gemini — это бесплатный вариант**
(`AI_PROVIDER=gemini`, значение по умолчанию, менять не нужно):

1. Зайти на https://aistudio.google.com/apikey и войти через Google-аккаунт.
2. Нажать «Create API key» — ключ создаётся сразу и бесплатно, без привязки
   карты (есть дневной лимит запросов, но для добавления карточек товара
   его более чем достаточно).
3. Положить ключ в переменную окружения `GEMINI_API_KEY` перед запуском сайта.
4. (Необязательно) `GEMINI_MODEL` — по умолчанию `gemini-flash-latest`
   (актуальный алиас Google на самую свежую модель Flash).

Второй готовый вариант — Anthropic Claude (платный): поставить
`AI_PROVIDER=anthropic`, получить ключ на https://console.anthropic.com/
(Settings → API Keys) и положить его в `ANTHROPIC_API_KEY` (модель
настраивается через `ANTHROPIC_MODEL`).

Если ключ выбранного провайдера не задан — кнопка вернёт сообщение «ИИ ещё
не настроен», ручное заполнение формы продолжает работать как обычно; это
best-effort функция, она не может ничего сломать в основном сайте. Из этой
песочницы нет прямого доступа в интернет ни к
`generativelanguage.googleapis.com`, ни к `api.anthropic.com` (та же
ситуация, что с Bitrix24 и Supabase выше), поэтому реальный вызов ИИ здесь
не тестировался живьём — сам эндпоинт `/admin/api/ai-fill` и вся обвязка
проверены (корректно возвращают «ИИ не настроен» без ключа и не ломают
форму), а сетевой запрос будет работать на реальном хостинге с обычным
интернетом и настоящим ключом.

## Структура проекта

- `app.py` — все роуты (публичный сайт, аккаунт, админка, API).
- `db.py` — слой данных (сейчас SQLite, см. выше про переезд на Supabase).
- `seed.py` — тестовые данные. Перезапускайте после изменений схемы.
- `translations.py` — словарь интерфейса RU/KK/EN.
- `helpers.py` — локализация полей, форматирование цены.
- `templates/` — Jinja2-шаблоны (публичный сайт, `account/`, `admin/`).
- `static/css/style.css` — вся вёрстка и дизайн-токены (палитра, шрифты).
- `static/js/main.js` — корзина (localStorage), допродажа, фильтры каталога,
  поиск, анимации появления при скролле.
- `supabase_schema.sql` — DDL для Postgres/Supabase (см. выше).
- `crm.py` — интеграция с Bitrix24 (см. раздел выше).
- `verify.js` — Playwright-скрипт для скриншот-проверки сайта (не часть
  продакшена, чисто QA-инструмент; можно удалить или оставить).

## Оплата (переменные окружения)

Способы оплаты включаются автоматически, как только заданы их переменные
окружения — ничего в коде менять не нужно (см. `payments.py`). Секретные
ключи никогда не хранятся в коде/README, только в окружении сервера.

**Freedom Pay** (карты, песочница уже настроена):
```
FREEDOMPAY_MERCHANT_ID=589392
FREEDOMPAY_SECRET_KEY=<ключ "для приёма" из личного кабинета my.freedompay.kz>
FREEDOMPAY_PAYOUT_SECRET_KEY=<ключ "для выплат" — пока не используется в коде>
FREEDOMPAY_TESTING=1   # поставить 0 для боевого режима, когда попросите менеджера переключить
```
`589392` — это ID **магазина** (Настройки → Магазины → «#589392 Amor
Flowers»), не ID аккаунта (80608) — их легко перепутать. В личном кабинете
уже проставлены и сохранены `RESULT URL` (`/pay/freedompay/callback`) и
`SUCCESS URL` (`/order/success`) для этого магазина.

⚠️ Перед боевым запуском обязательно сделать один тестовый платёж в
песочнице и проверить в логах, что `PAY.freedompay_verify()` в
`/pay/freedompay/callback` возвращает `True` — схема подписи для входящего
`result_url` не была явно расписана в открытой документации Freedom Pay,
реализация — по лучшей практике для этого семейства протоколов (PayBox).
Если не сойдётся — написать менеджеру Freedom Pay (+7 705 717 87 16,
указан в личном кабинете) с вопросом «какой script name использовать при
проверке pg_sig во входящем result_url запросе».

**Kaspi Pay / Halyk ePay / PayPal** — см. переменные в начале `payments.py`
(`KASPI_MERCHANT_ID`/`KASPI_API_KEY`, `EPAY_TERMINAL_ID`/`EPAY_CLIENT_ID`/
`EPAY_CLIENT_SECRET`, `PAYPAL_CLIENT_ID`/`PAYPAL_SECRET`) — пока не
подключены.

**Доставка в structured data**: по умолчанию в `shippingDetails` указана
ставка **1500 ₸** (задано как дефолт в коде). Если ставка изменится — либо
поменять дефолт в `app.py` (`config_delivery_rate_kzt`), либо задать
переменную окружения `DELIVERY_RATE_KZT` — она имеет приоритет.

4. Добавить настоящие фото товаров (сейчас — декоративные SVG-заглушки,

5. Подключить реальный домен и WSGI-сервер (сейчас — dev-сервер Flask,
   `debug=True`; для продакшена — gunicorn/uwsgi + nginx, и обязательно

6. Отзывы 2ГИС — на сайте сейчас 8 реальных отзывов, скопированных вручную

   `/admin/reviews`, оттуда же можно удалять.
7. Пересмотреть RLS-политики в Supabase, если решите подключать его
   напрямую с фронтенда (см. раздел выше).

## Известные ограничения прототипа

- Оплата — только «подтверждение оператором» (COD-модель), онлайн-эквайринга
  нет (как и просили).
- Фото товаров — плейсхолдеры (цветной прямоугольник с иконкой), не
  настоящие снимки. Загружаются через `/admin/products` → редактировать
  товар → поле «Фото товара» (JPG/PNG/WebP, до 8МБ) — после загрузки фото
  сразу заменяет плейсхолдер на карточках и странице товара.
- Локальный запуск не тестировался против реального Supabase (нет сети из
  этой песочницы) — только против SQLite.

## Про "database is locked" (уже починено)

Во время тестирования нашёл и починил реальный баг в `db.py`: при ошибке
внутри функции записи (например, если форма прислала несуществующий
`category_id`) соединение с базой не закрывалось и оставалось с открытой
транзакцией — это блокировало файл базы, и следующий же корректный запрос
на запись (заказ, сохранение товара и т.п.) падал с
`sqlite3.OperationalError: database is locked`, пока сервер не
перезапускали. Теперь все функции записи используют общий контекстный
менеджер `write_conn()`, который гарантированно коммитит/откатывает и
закрывает соединение в любом случае — ошибка в одном запросе больше не
блокирует остальной сайт.


## Безопасность (обновлено 2026-09-02)

Запуск теперь требует переменных окружения:

```bash
SECRET_KEY=<длинная случайная строка> python3 app.py
```

Без `SECRET_KEY` ключ генерируется случайно на процесс — сайт работает,
но сессии слетают при перезапуске. Отладчик выключен: включается только
явным `FLASK_DEBUG=1` и **никогда** не должен быть включён на публичном адресе.
За HTTPS добавьте `FORCE_SECURE_COOKIES=1`.

Пароль админа при засеве:

```bash
ADMIN_PASSWORD=<ваш пароль> python3 seed.py
```

Без переменной пароль генерируется случайно и печатается один раз — запишите его.
